## GitHubをひと言でいうと

**GitHubは、Gitで管理しているファイルの履歴をインターネット上に置き、みんなで共同作業するための場所** です。

| | Git | GitHub |
|---|---|---|
| 何か | バージョン管理の道具 | Gitの履歴を置くWebサービス |
| どこで動くか | 自分のパソコン | インターネット上 |
| 主な役割 | 変更の記録・巻き戻し | 共有・レビュー・自動化・公開 |

Gitだけでも履歴は残せますが、GitHubを使うと「人に見せる」「意見をもらう」「自動でテストや公開をする」ことができるようになります（[GitHubとは](/how-to-use-github/01-what-is-github/)）。

## 5つの言葉で全体をつかむ

GitHubの操作は、ほとんどが次の5つの言葉の組み合わせです。

| 言葉 | ひと言でいうと | たとえるなら |
|------|----------------|--------------|
| リポジトリ | プロジェクトのフォルダと、その全履歴 | 1冊のノート |
| コミット | 変更をひとまとまりで記録したもの | ノートに付ける「保存した日付つきの付箋」 |
| ブランチ | 本筋から分かれた作業用の流れ | ノートのコピーで下書きする |
| プルリクエスト（PR） | 「この変更を取り込んでください」というお願い | 下書きを清書に写す前の確認依頼 |
| マージ | ブランチの変更を本筋に取り込むこと | 清書に写す |

```
main     ──●──────────────●──── （常に動く状態を保つ本筋）
             \            /
feature       ●───●───●─      （作業用ブランチでコミットを重ねる）
                       ↑
                 プルリクエストでレビューしてマージ
```

## チーム開発の基本の流れ

GitHubでの共同作業は、次の流れの繰り返しです。

1. **ブランチを作る**：mainから作業用のブランチを分ける
2. **コミットする**：作業の区切りごとに変更を記録する
3. **プッシュする**：手元のコミットをGitHubに送る
4. **プルリクエストを作る**：変更内容を説明して、レビューを依頼する
5. **レビューを受けてマージする**：OKが出たらmainに取り込む

:::tip[ポイント]
「mainは常に動く状態に保ち、作業はブランチで行う」。この1つのルールを守るだけで、チーム開発の事故の多くが防げます（[ブランチ管理](/how-to-use-github/05-branch-management/)）。
:::

## 画面の地図：リポジトリのタブ

リポジトリのページ上部には、次のタブが並んでいます。最初はこの5つだけ覚えれば十分です。

| タブ | やること |
|------|----------|
| Code | ファイルを見る・編集する、ブランチを切り替える |
| Issues | やること・不具合・アイデアを記録する |
| Pull requests | 変更のレビューとマージ |
| Actions | テストやデプロイの自動実行を見る |
| Settings | 公開範囲・権限・保護ルールの設定 |
